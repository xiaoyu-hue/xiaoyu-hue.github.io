九溪:把一个信息流装进静态站,代价是什么

2026-10-11 · 项目故事 · jiuxi
信息聚合Astro 7第一方代理报刊版式

这个项目的出发点不太体面:我每天被信息喂得很饱,却总觉得自己漏掉了什么。更麻烦的是约束有三条——我不会后端,手上只有一台手机,写出来的东西最终只能推到 GitHub。这三条加在一起,基本堵死了"自己跑个正经服务端"这条路。

起因:我只有一个手机,和一堆想收进来的信息

我想看的挺杂:AI 的新进展、当天值得知道的新闻、科技圈在吵什么、AI 发展到哪一步了、有什么工具好用、最近有什么书值得读。拆开看是每个都有自己的 App 和网站,合起来是我每天要在六七个标签页之间来回跳。

现成的聚合工具不少,但它们要么要注册,要么插广告,要么替我决定"你应该看什么"。我想要的其实很朴素:把入口收拢到一个地方,然后把判断权留给我自己。

三条约束摆平之后,路就只剩一条:站点本身是纯静态的,push 上去就上线;而"实时资讯"这件事,交给每一位访客自己的浏览器去干。

它现在长什么样

十个板块:首页聚合、AI、热点新闻、科技、AI 发展时间线、AI 工具箱、游戏娱乐、读书推荐、设置与数据、关于九溪。其中工具箱和读书是我自己一条条挑的——工具箱做到 40 条(v1.3.0 一次补了 23 个,把"智能体/Agent"这条主线补齐),读书扩到 37 本(每本配客观推荐语和可在线阅读的链接,技术之外的历史、哲学、非技术向 AI 入门也在里面)。

技术上它是 Astro 7 + Tailwind CSS 4 + TypeScript,输出的是一整个文件夹的静态文件,没有一个需要跑着的进程。时间线、工具箱、读书这些我自己写的内容存在仓库的 Markdown 里,用 Content Collections 管理并做 Zod schema(数据结构契约)校验——改一篇文章就是改一个文件,手机上的 GitHub 网页也能提交。

视觉上我做了件有点执拗的事:全站改成报刊版式——暖白纸底、墨色字、单一强调色、自托管的中文衬线字体。没有渐变,没有玻璃拟态。

我拍板的三个决定

1. 资讯交给浏览器去抓,代价是永远依赖别人的接口

常规做法是自己写个定时任务抓一遍存起来。我不会后端,也不想为一台服务器付钱。所以九溪的做法是:页面加载后,由访客的浏览器直接请求公开数据源,抓完在浏览器里缓存 30 分钟。

数据源包括 Google News RSS、Hacker News(Algolia)、ArXiv cs.AI、IT之家、爱范儿、RSSHub、TechCrunch、Ars Technica 等,直连优先。好处是零运维、结果永远新鲜、我这边不存任何人的任何数据。代价非常直接:源站改版我就抓不到,限流我就抓不到,被拦我也抓不到。这不是能修复的 bug,是这个选择的账单。

2. 同域代理绕开跨域限制,代价是我得自己写防护

浏览器有条安全规则叫 CORS(跨域资源共享):A 站点的页面不能直接去读 B 站点的数据。这条规则挡住了绝大部分第三方 RSS。于是只能有个中间人——九溪在 Cloudflare Pages Functions 上跑了一个同域代理 /api/feed,对浏览器来说它和站点同源,规则就放行了。

但代理一旦放开,就成了别人拿来打内网的跳板(这类攻击叫 SSRF)。所以我给它加了目标白名单和 SSRF 防护:不在名单里的源一律不代理。代价是灵活性——想加一个新数据源,得先改配置再重新部署,不能在页面上随手填。

还有个连带后果:GitHub Pages 备站跑不了 Functions,所以备站上的资讯是构建期注入的快照,不实时。这是"双站容灾"必须接受的不对称。

3. 把 AI 生成站的那张默认脸删掉

渐变背景配玻璃拟态面板,现在是 AI 生成页面的标准长相。九溪早期也是这个样子,看久了只有一个感觉:不像我。

于是在 v1.2.0 里整套重做:实色面板、1px 发丝边、分层细阴影取代毛玻璃;主题改成"纸感底 + 墨色字 + 单一强调色"的四套(晨曦/午夜/极光/樱粉);字体用 @fontsource 子集化后自托管,零外链请求。动效也压到几乎察觉不到——滚动渐显、卡片流过渡、Lenis 平滑滚动,全都带降级守卫,并尊重系统的 prefers-reduced-motion(减弱动态效果)设置。

代价是重写了整套视觉层,还得专门写一份 DESIGN.md 当唯一凭据,免得下一轮改动又把风格带跑偏。

一个我自己引进的安全缺陷

v1.2.0 那轮代码梳理里,我们查出一处我自己写出来的漏洞:构建脚本 fetch-feeds.mjs 在构建期把远端抓来的资讯标题塞进页面的数据块,却没有做转义。这意味着一条标题里只要含有 </script>,就能提前把脚本块闭合掉,接着往页面里放它想放的东西——这就是常说的存储型 XSS(跨站脚本)。

修起来其实不难,把危险字符转义掉就行。但这条记录我特意留在 CHANGELOG 里没删。因为它是这个项目的真实组成部分:一个不会写代码的人用 AI 搭出来的东西,里面一定有我读不懂也想不到的角落。躲开这类问题的办法不是假装它不存在,而是定期去翻,翻到了就如实记下来。

同一轮还把 Astro 从 5.18.2 升到 7.3.8,修的是一个 CRITICAL(最高危)级依赖漏洞——这条此前漏记了,是那次补上去的。

诚实清单:它做不到什么

  • 脱离第三方数据源 — 源站改版、限流或被拦,对应板块就会空着
  • 备站实时 — GitHub Pages 没有 Functions,资讯只能是构建期快照
  • 随手加数据源 — 代理带白名单,加源要改配置重新部署
  • 保证星数准确 — 工具箱里的星数是公开数据的约值,会随时间变动
  • 替你判断价值 — 它只负责把东西摆到一处,什么值得看仍然由你决定
  • 在受限网络里照常工作 — 抓取依赖外网可达,部分公司或校园网关会直接拦掉

回过头看

九溪证明的不是"AI 能多快写出一个站",而是受约束的人怎么把约束本身变成方案:不会后端,就让每位访客的浏览器替我去抓;想要实时,就接受永远依赖别人的接口;想要双站容灾,就接受两个站点并不对等。

每一个被满足的需求背后,都挂着一张代价清单。我把它们写进页头、文档和这里的"诚实清单",而不是藏起来。因为"看起来什么都能做到"很容易,但那不是我要的东西。
